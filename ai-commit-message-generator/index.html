This tool builds a clean commit message in the Conventional Commits style from a change type, scope and short description. It checks your first line against the 72-character guide and adds an optional body and footer.

This tool formats a message; it does not commit code or touch your repository. Paste the message into your own commit step. This tool works fully in your browser and calls no AI service, API, or backend.

How to use this generator

Pick the change type that fits your work, add a scope if the change belongs to one part of the project, and write a short description of what changed. Add a body if the reason needs explaining, and a footer if the change closes an issue.

Press the button and the tool builds the message in the Conventional Commits format: type, optional scope in brackets, a colon, then the description. It also checks the first line against the 72-character guide and tells you the exact count.

Why the 72-character guide exists

Commit histories are read in narrow places: terminal windows, log views, and short summaries. A first line of 72 characters or fewer fits comfortably in those places without wrapping, so the whole change is visible at a glance.

The guide is about the first line only. The body below it can be as long as it needs to be, because it is read separately. If your description will not fit in 72 characters, shorten the description and move the detail into the body.

Picking the right change type

Use feat when you add something users can see or use, and fix when you repair something broken. Docs, style, and test changes are what they sound like. Refactor is for restructuring code without changing what it does, and perf is for making it faster.

Build, ci, and chore cover the work around the code: dependencies, pipelines, and routine tasks. Revert is for undoing an earlier commit. If two types seem to fit, pick the one that describes the main change and mention the other in the body.

Honest limits

This tool formats the message you describe. It cannot see your code, check whether the description matches the change, or know whether the type you picked is the right one. Read the message once against your actual change before you commit.

Teams sometimes use their own conventions on top of Conventional Commits. If your team has rules about scopes, footers, or issue references, follow those rules and use this tool for the shape of the message.

Questions people ask

What is Conventional Commits?

It is a simple format for commit messages: a change type, an optional scope, and a short description, like feat(login): add password reset link. The format makes history easy to scan and to search.

What goes in the scope?

The part of the project you changed, in one or two words, such as login, api, or docs. The scope is optional; leave it out if the change touches the whole project.

Why keep the first line under 72 characters?

Short first lines fit in log views and terminal windows without wrapping, so the whole change is visible at a glance. Put extra detail in the body instead.

Does this tool commit my code?

No. It builds the message text. You paste it into your own commit step; nothing here touches your repository.
